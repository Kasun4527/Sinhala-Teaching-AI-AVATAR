**How Files are Handled (Answering your question!):**

The Admin Portal will send this entire `.zip` file to the Backend's new endpoint. 
The Backend will then:
1. Unzip the file.
2. Save the `.txt` files into its `backend/documents_unicode/` folder.
3. Save the images into its `backend/images/` folder so they can be served to the frontend.
4. Read the text and safely ingest it into its local ChromaDB.

## 2. Database Unification Options & Tradeoffs

Currently, the Backend uses the `ai_avatar` database, and the Admin Portal uses the `sinhala_admin` database. Here are the options to unify them so that the Backend's dashboard can see the teachers and lessons created by the Admin Portal.

### Option 1: Complete Merge (Recommended)
Both services connect to the `ai_avatar` database. 
- Admin users and Teachers go into the backend's `users` collection with `role: "admin"` and `role: "teacher"`.
- Lessons and Subjects go into the backend's `subjects` and `topics` collections.
- **Tradeoffs**: 
  - ✅ Simplest data model (one source of truth for "users").
  - ✅ Dashboards in the backend can immediately query all users.
  - ❌ Requires slightly modifying the Admin Portal's code to map its `app_data` schema (e.g. `first_name`, `last_name`) to the Backend's existing `User` Pydantic schema (e.g. `username`, `email`).

### Option 2: Shared Database, Separate Collections
Both services connect to the `ai_avatar` database, but the Admin Portal keeps using its own separate collections (e.g., `admins`, `admin_teachers`, `admin_lessons`).
- **Tradeoffs**:
  - ✅ Very easy to implement. Minimal changes to Admin Portal code (just change the database name).
  - ❌ The backend dashboard won't automatically see the new teachers or lessons unless you update the backend's dashboard agent queries to look at these *new* collections instead of the existing ones.

### Option 3: REST API Bridge for Database (Keep Databases Separate)
Leave the databases completely separate. When the Admin Portal creates a teacher or lesson, it sends an API request to the Backend, and the Backend inserts it into `ai_avatar`.
- **Tradeoffs**:
  - ✅ Zero risk of breaking backend database schemas.
  - ❌ Data duplication. You now have the same teacher stored in `sinhala_admin` and `ai_avatar`.
  - ❌ High complexity (need to handle API failures, updates, and deletes across two systems).

## 3. Auth Unification (How to use the same SECRET_KEY)

Since you want a single unified login, an admin logging into the frontend should receive a JWT token that is valid for *both* the Next.js frontend (talking to Backend) and the Admin Portal backend.

**How to do it without breaking the backend:**
1. Open the Backend's `.env` file and locate the existing `SECRET_KEY`.
2. Open the Admin Portal's `.env` file and set its `SECRET_KEY` to the **exact same value**.
3. Both systems currently use the identical JWT algorithm (`HS256`) and the identical `python-jose` library. 
4. Because the secret keys match, a token generated by the Backend's login route can be seamlessly verified by the Admin Portal's `get_current_admin` dependency without a single code change.

## 5. Independent Deployment Tradeoffs

You requested to keep the Admin Portal deployable independently via its existing standalone GitHub Action workflow (`deploy.yml`).

**Tradeoffs of Independent Deployment:**
- ✅ **Safer for the Backend**: You can push updates, bug fixes, and changes to the Admin Portal multiple times a day without triggering a rebuild or restart of the critical student-facing Backend.
- ✅ **Faster CI/CD**: Building and deploying just the Admin Portal takes 2 minutes. Deploying a monorepo takes much longer.
- ❌ **Version Skew Risk**: If you update the shared REST API bridge format in the Backend, you must remember to manually deploy the Backend *before* deploying the Admin Portal, otherwise they will be out of sync.
- ❌ **Duplicated Secrets**: You have to manually ensure the Azure Container Apps for both services have matching environment variables (like `SECRET_KEY`).

**How to maintain it:**
Leave `.github/workflows/deploy.yml` exactly where it is inside the `admin_portal/` folder. When you want to deploy *only* the admin portal, you can run this workflow manually via GitHub Actions (using `workflow_dispatch`), or configure it to only trigger when files inside `admin_portal/**` are changed.
